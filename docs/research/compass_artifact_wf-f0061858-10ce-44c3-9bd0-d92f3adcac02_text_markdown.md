# Portando um Framework Agêntico para o Microsoft Copilot Studio (2025–2026): Mapa Conceito-a-Recurso, Lacunas e Estratégia para Ambiente Farmacêutico Regulado

## TL;DR
- **Copilot Studio cobre a maior parte da topologia do framework** (orquestrador + subagentes, ferramentas, conhecimento, ALM, audit logs, HITL, BYOM) — mas com lacunas críticas para o uso farmacêutico regulado: **isolamento de contexto entre agentes é opt-in (history pass-through é o default)**, **não há versionamento nativo de prompts/instruções de agente comparável a Git de specs**, e **o orquestrador generativo é probabilístico** (incompatível com pipelines determinísticos PMO→explorer→developer→qa-critic→docops sem ancoragem em "agent flows" ou Power Automate).
- **A estratégia certa é HÍBRIDA**: manter o repositório `.agent/` + AGENTS.md como **single source of truth normativa** (versionada em Git, fonte para validação GAMP 5/CSA), e usar Copilot Studio **apenas como camada de interação/distribuição** (Teams, web, M365) que delega execução crítica para (a) **Power Automate "agent flows" com multistage approvals** (caminho determinístico, audit-trail nativo) e (b) **Azure AI Foundry Agent Service / Microsoft Agent Framework 1.0** (lançado em 3 de abril de 2026 como "production-ready release: stable APIs, and a commitment to long-term support") para o pipeline adversarial e modelos distintos developer/qa-critic.
- **Para o ambiente farmacêutico (ANVISA/GAMP 5/ALCOA+)**: Copilot Studio sozinho é INSUFICIENTE como sistema de registro — use-o como UI low-code, mas instrumente Application Insights + Microsoft Purview + Dataverse com retenção estendida + ADRs/changelog mantidos no Git do repo agêntico. **A camada de "constituição" e a `validation-gamp5` skill devem permanecer fora do Copilot Studio**, porque hoje a plataforma não oferece versionamento granular de instrução por agente nem assinatura eletrônica 21 CFR Part 11/Annex 11 nativa.

## Key Findings

1. **Orquestração multi-agente existe e amadureceu em 2025–2026**, com dois sabores oficiais — **Connected Agents** (agentes independentes publicados, com seu próprio runtime; ideal para mapear `developer`, `qa-critic`, `docops`) e **Child/Inline Agents** (sub-rotinas dentro do agente pai; compartilham contexto). [CONSOLIDADO / CONFIRMADO — Microsoft Learn, "Add other agents overview"]. **Agent-to-Agent (A2A)**, integração com Microsoft Fabric, e Microsoft 365 Agents SDK orchestration foram anunciados em GA progressiva pelo Microsoft Copilot Blog ("New and improved: Multi-agent orchestration, connected experiences, and faster prompt iteration", 1 de abril de 2026, Nitasha Chopra): "These features will be fully available to all eligible customers as of April 2026."
2. **Contexto NÃO é fresco/isolado por default em connected agents**: a opção "Pass conversation history to this agent" vem **marcada por padrão**. Microsoft Learn ("Add a Copilot Studio agent as a connected agent") instrui literalmente: *"If you want to prevent conversation history from being passed to this agent when another agent calls it, clear the **Pass conversation history to this agent** box. This method limits the information being passed to the agent to just the explicit task that the main agent wants the other agent to complete."* Em inline/child agents, o compartilhamento de contexto é estrutural — *"Inline agents share context with the main agent, so passing data between them is simple"* (Microsoft Learn, "Explore multi-agent orchestration patterns") — e **não há toggle de isolamento documentado**. [EMERGENTE / CONFIRMADO]
3. **Reutilização de instruções/conhecimento (`_shared/`)** é coberta por **Component Collections**, declaradas em GA no Microsoft Copilot Blog "What's new in Copilot Studio: September 2025": *"Managing copilots across environments is simpler with the component collection capability, now generally available in Copilot Studio."* Empacota tópicos, knowledge sources, ações e entidades em uma coleção versionada como solução gerenciada do Power Platform, com agente "primário" + agentes consumidores e permissões Viewer/Editor. [CONSOLIDADO / CONFIRMADO]. Tools page também provê reutilização cross-agent de ferramentas individuais. [CONSOLIDADO / CONFIRMADO]
4. **ALM existe e é robusto via Power Platform**: solutions (managed/unmanaged) + environment variables + connection references + **Power Platform Pipelines** + **Git/Azure DevOps source control nativo** com formato YAML. Componente do solution é o `botcomponent` em Dataverse [CONSOLIDADO / CONFIRMADO — Microsoft Learn "Establish an ALM strategy"]. **Lacuna**: o "system prompt"/instruções de um agente vive dentro da solution como blob, **não há diff granular por linha de instrução comparável a um prompt versionado em Git puro**.
5. **HITL maduro**: **Multistage Approvals** (manual + AI + condicional) e **Request for Information** em agent flows (preview/GA progressiva) cobrem o "gate humano obrigatório" do framework, com card actionable via Outlook/Teams e callback ao agente [EMERGENTE / CONFIRMADO — Microsoft Learn "Multistage and AI approvals in agent flows"]. Power Apps MCP Server `request_assistance` e `invoke_data_entry` permitem agentes autônomos pausarem para revisão humana antes de gravar em Dataverse [EMERGENTE / CONFIRMADO].
6. **Audit trail nativo é parcial**: Microsoft Learn ("Develop a custom analytics strategy") confirma a retenção default curta: *"By default, both sources have a data retention of 30 days. You can change the retention period for conversation transcripts in Dataverse."* Application Insights opcional (pago, Azure); audit logs administrativos e de usuário em **Microsoft Purview**, com schema dedicado para Copilot Studio. Para retenção estendida exigida em GxP, é **mandatório** exportar via Azure Synapse Link para Azure Data Lake Storage Gen2 [CONSOLIDADO / CONFIRMADO — Microsoft Learn "Monitor operations, compliance, and capacity"]. **Lacuna ALCOA+**: nada nativo garante imutabilidade tipo WORM nem assinatura eletrônica 21 CFR Part 11 — é necessário Azure Storage Immutable Blob + Purview retention locks + processo SOP externo.
7. **Compliance da plataforma**: Copilot Studio é coberto por **HIPAA BAA, HITRUST CSF, FedRAMP, SOC, ISO 27001/27018/27017/27701, PCI DSS, CSA STAR** [CONSOLIDADO / CONFIRMADO — Microsoft Learn "Review ISO, SOC, and HIPAA compliance"]. **NÃO há atestação GxP/GAMP 5 específica para Copilot Studio** — a Microsoft publica "GxP qualification guidelines" para Office 365/Azure mas Copilot Studio **não está listado como serviço qualificado GxP**; o framework GAMP 5/CSA precisa ser aplicado pela própria empresa farmacêutica como integradora.
8. **MCP é suportado e GA** desde 2025 (transport streamable HTTP; SSE depreciado após ago/2025) — permite plugar tools externas com OAuth 2.0/DCR e ACP/DLP. **Pré-requisito**: generative orchestration ligada. Toggle por-ferramenta `Allow all` para enforço de menor privilégio [CONSOLIDADO / CONFIRMADO — Microsoft Learn "Extend your agent with Model Context Protocol"].
9. **Memória persistente nativa é fraca**: variáveis globais existem apenas durante a sessão; persistência entre sessões depende de **Dataverse + lookups manuais** ou storage externo. Não há equivalente direto e nativo a `.agent/brain/history.md` com semântica de "memória episódica entre conversas" [EMERGENTE / INFERIDO — Microsoft Learn "Variables overview" + análise do gap].
10. **Bring Your Own Model (BYOM)**: dois níveis. **Por prompt/tool** está GA (modelos de Azure AI Foundry, inclusive Llama/Grok/Deepseek/fine-tuned). **Per-agent "Primary response model" via Azure AI Foundry está em PUBLIC PREVIEW desde março/2026** (Power Platform release plan 2025 Wave 2, "Use your own model when generating responses"), com instruções verbatim do Microsoft Learn: *"When you bring your own model (BYOM) to response generation, you add your custom model deployed in AI Foundry. This approach gives you more tailored answers that fit specific domains. First, go to the agent settings. Use the response models list to add a new model. Enter the AI Foundry deployment connection details for your model."* Esta capacidade viabiliza usar GPT-5 para developer e Claude/Llama para qa-critic, sustentando a revisão adversarial com modelos distintos [EMERGENTE / CONFIRMADO]. Limitação documentada: *"Data processed within the preview may be processed and stored outside of your organization's geographical boundary"* (Microsoft Learn, "Choose a model for generative responses") — bloqueia uso em produção GxP enquanto não GA.
11. **Limitações estruturais**: (a) **custo opaco em Copilot Credits** — Microsoft Learn ("Billing rates and management") declara: *"It's billed as Text and generative AI tools (premium) per 10 tokens, at 100 Copilot credits"*; um agente complexo facilmente consome 12+ créditos por resposta (generative answer = 2 créditos + tenant graph grounding = 10 créditos), com pacotes de 25.000 créditos = US$ 200/mês ou US$ 0,01/crédito PAYG; (b) **degradação do orquestrador generativo** documentada literalmente pela Microsoft em "Add other agents overview" (atualizado 2026-04-09): *"As a rule of thumb, this degradation in performance can happen when your main agent has more than 30-40 choices of action (tools, topics, and other agents). However, degraded performance can also happen in an agent with a smaller number of tools with similar descriptions. … splitting functionality across multiple agents can help to maintain precision"*; (c) **prompt versioning intra-agent inexistente** comparado a Git; (d) **lock-in Dataverse/Power Platform**; (e) **latência adicional por hop** em multi-agent; (f) **fallback message default não pode ser sobrescrito** por instruções customizadas.
12. **Caminho recomendado**: **coexistência**, não substituição. O repositório `metacognition-framework` continua sendo a fonte normativa (Git + ADRs + skills `_shared/`). Copilot Studio recebe um **subset operacional** (ex.: PMO front-end no Teams + connected agents para developer/qa-critic), com o pipeline crítico-regulado **fora** dele (Microsoft Agent Framework 1.0 + Foundry Agent Service para o qa-critic adversarial com modelo distinto). Camada constitucional e validation-gamp5 ficam no Git, jamais migradas, para preservar single-source-of-truth e CSV.

### Detalhamento por questão

**1. Orquestração multi-agente.** Copilot Studio oferece três modos de composição: (a) **inline/child agents** — agentes leves dentro do principal, herdam contexto e ferramentas; (b) **connected agents** — agentes independentes, com seu próprio runtime, tools e knowledge, com o orquestrador pai roteando por descrição/intent; (c) **A2A protocol** para agentes em outros runtimes (Microsoft 365 Agents SDK, Foundry, Fabric Data Agents). Microsoft documenta explicitamente que "splitting functionality across multiple agents can help to maintain precision" quando o agente passa de 30–40 escolhas. Mapeie **PMO = main agent**, **explorer/developer/qa-critic/docops = connected agents publicados separadamente**. A pipeline sequencial determinística do framework (que exige ordem PMO → explorer → developer → qa-critic → docops) **não é o forte da generative orchestration** — ela é "self-assembling". Para preservar a ordem, encapsule o pipeline em um **agent flow** (Power Automate) que chama os agentes via action `ExecuteCopilotAsyncV2` em sequência, com approval gates entre eles.

**2. Contexto isolado.** Por design, Copilot Studio **passa as últimas 10 turnos de histórico** para o planner. Em connected agents há o toggle citado em Key Findings — desmarque-o para isolar. Em inline/child o compartilhamento é estrutural. Variáveis globais vivem na sessão; ambientais são read-only e por ambiente. Para o seu princípio de "menor privilégio cognitivo", o padrão correto é: **(a) connected agents com history-off**, **(b) passar somente parâmetros explícitos via topic inputs**, **(c) `Clear variable values` node antes de cada redirect, escopo "Conversation history for the current session"**, conforme guidance Microsoft. Esse comportamento é mais frágil do que o "fresh context" garantido por subagentes do Claude Code/GitHub Copilot — o opt-out é manual e auditável apenas por log.

**3. Skills reutilizáveis.** **Component Collections** (GA setembro/2025, conforme blog oficial citado) é o equivalente mais próximo de `_shared/`. Permite empacotar tópicos, knowledge, ações e entidades; conecta múltiplos agentes consumidores; updates propagam automaticamente; suporta export como **managed solution** para mover entre DEV/TEST/PROD. Compartilhamento com permissões Viewer/Editor. Para **`validation-gamp5`** que precisa de hash imutável + ADRs: **mantenha no repositório Git** e importe-a no Copilot Studio como **knowledge source SharePoint** (até 200 MB por arquivo no Work IQ semântico) — assim a fonte normativa segue versionada fora da plataforma, e o agente apenas consulta.

**4. SDD/ALM.** Copilot Studio é solution-aware (Dataverse) com (a) **environment variables**, (b) **connection references**, (c) **Power Platform Pipelines** (citizen-friendly), (d) **GitHub Actions for Power Platform**, (e) **Azure DevOps integration**, e (f) **Native Git sync em YAML** (Power Apps/Power Automate/Pages/Copilot Studio). Estrutura: `Solutions/[Name]/{botcomponents/, bots/, connectionreferences/, environmentvariabledefinitions/, publishers/, solutions/}`. **Limitação importante**: alguns artefatos **não são solution-aware** (autenticação, channels, sharing settings) — precisam de runbook de pós-deploy. Para SDD, o pattern é: o `.md` da especificação atômica continua em Git; `bots/*.yml` exportado é commitado lado a lado para diff; pipeline CI valida que o YAML do agente reflete a spec.

**5. HITL.** Use **agent flow** com **multistage approval** (manual + AI + condicional), **Request for Information**, ou **Power Apps MCP Server (`request_assistance`, `invoke_data_entry`)** para pausar execução até resposta humana (callback assíncrono). Padrão "diagnose → propose → execute" com duplo approval gate antes de ações irreversíveis é doc-pattern oficial.

**6. Rastreabilidade/audit.** Quatro camadas: (1) **Dataverse `conversationtranscripts` table** (default 30 dias conforme verbatim do Microsoft Learn citado — claramente insuficiente para GxP: estenda via Azure Synapse Link → ADLS Gen2 com retenção configurável); (2) **Application Insights** com Copilot Studio Dashboard built-in (KQL para queries customizadas, eventos como `GenerativeAnswers`, latência, exceções, tool calls); (3) **Microsoft Purview Audit** com schema dedicado Copilot Studio (admin events + user interactions); (4) **Microsoft Sentinel** para SIEM. **Para ALCOA+**: nenhum dos 4 é imutável-por-default — combine Purview retention locks + Azure Immutable Blob Storage + audit-log forwarder para escrita-uma-vez.

**7. Conformidade regulada.** Copilot Studio tem atestações HIPAA/HITRUST/FedRAMP/SOC/ISO/PCI/CSA STAR documentadas. **Não há atestação GxP/GAMP 5 específica** — a Microsoft publica "GxP Qualification Guidelines" para Office 365 e Azure como insumo, mas Copilot Studio (como serviço) **deve ser validado pelo cliente** seguindo CSA risk-based approach (FDA 2025) / GAMP 5 2nd Ed. Para ANVISA RDC 658/2022 (validação de sistemas computadorizados) e Annex 11 EU, o serviço é "category 4 — configured product" — o burden de validação operacional (IQ/OQ/PQ) recai sobre o regulado. **LGPD/DPIA**: Dataverse oferece data residency (incluindo Brazil South), mas preview features de Copilot Studio podem processar dados fora da fronteira — bloquear preview em prod.

**8. Tools/MCP/menor privilégio.** MCP é GA. Cada MCP server vira um connector Power Platform sujeito a **DLP policies, ACP, Conditional Access, Network Isolation**. Toggle `Allow all` permite habilitar/desabilitar tools individuais. **Entra Agent ID (preview)** dá a cada agente um service principal próprio no Entra com API permissions visíveis ao admin — Conditional Access enforced hoje **apenas no canal Teams**; outros canais usam o flow tradicional do connector. **Autenticação OBO** disponível para custom connectors com Entra ID — permite agente agir em nome do usuário com o token deste. Para autonomous agents (sem usuário interativo): **maker-provided credentials** = service-account style, exige hardening (rotação, monitoramento, escopo mínimo).

**9. Memória persistente.** Variáveis globais expiram com sessão. Para persistência cross-session, o padrão é **modelar tabelas custom em Dataverse** ("AgentMemory", "DecisionLog", "ConfidenceClassification") e ler/escrever via connector Dataverse ou agent flow. Não há equivalente nativo a `brain/history.md`. **Compaction de contexto longo** pode ser feito via Clear variable values + reset topic, mas resumos persistentes precisam ser implementados manualmente.

**10. Modelo subjacente e BYOM.** Modelo default = GPT-4/4.1 (e GPT-5 quando ativado). Per-prompt BYOM (Azure AI Foundry) é GA: catálogo 1900+ modelos, inclusive fine-tuned. **Per-agent Primary Response Model via Azure AI Foundry está em PUBLIC PREVIEW desde março/2026** (Power Platform release plan 2025 Wave 2). Isso viabiliza o **qa-critic com modelo distinto do developer** (princípio adversarial do framework) — ex.: developer=GPT-5, qa-critic=Claude Sonnet 4.6 ou Llama 4 Maverick. **Bloqueador para GxP**: preview features podem processar dados fora da geografia; aguarde GA ou contorne implementando qa-critic em **Foundry Agent Service / Microsoft Agent Framework 1.0** (lançado em produção em 3 de abril de 2026), chamando o agente Copilot Studio só como consumidor da decisão.

**11. Limitações/antipadrões.**
- **Custo**: Microsoft Learn formaliza o premium rate de reasoning models em "100 Copilot credits per 10 tokens" (Text and generative AI tools premium meter). Pacotes de 25.000 créditos = US$ 200/mês; PAYG = US$ 0,01/crédito. Cenário típico de "5 agentes" estimado em US$ 3.000–6.000/mês só em créditos (CloudZero). Estoque mensal não rola para o próximo mês. **Antipadrão**: usar generative orchestration para tudo — preserve "classic answers" e "agent flows" determinísticos onde não há ambiguidade.
- **Latência**: cada hop multi-agente adiciona overhead; flows de >2 min falham retornando ao agente.
- **Prompt versioning**: instruções de agente são blobs dentro do solution; sem diff por linha tipo Git.
- **Lock-in**: dependência forte de Dataverse, Power Platform connectors, Copilot Credits. Migrar para fora é re-escrita.
- **Degradação do orquestrador**: a regra documentada Microsoft é 30–40 tools/topics/agents antes de degradar precisão — força arquitetura multi-agent.
- **Fallback message**: "I'm sorry, I'm not sure how to help with that" não é sobrescrevível por custom instructions — apenas editando o Fallback system topic.
- **Generative orchestration em outras línguas** chegou a GA em 2025 mas algumas integrações (ex.: certas preview models) seguem en-US only.

**12. Estratégia de portabilidade/coexistência.** O framework existe hoje como repo `.md` (Claude Code, GitHub Copilot custom agents `.agent.md` com subagentes nativos e handoffs). **Não migre o framework para dentro do Copilot Studio**. Em vez disso:

1. **Mantenha o repo Git como camada normativa**: AGENT-FRAMEWORK.md, AGENTS.md, CLAUDE.md, `_shared/`, ADRs, changelog, validation-gamp5. Esta camada serve à validação CSA/GAMP 5 (é o "design specification" do sistema).
2. **Use Copilot Studio para a camada de UX/distribuição** (Teams, web embed, M365 Copilot Chat) e para agentes operacionais não críticos (ex.: front-end PMO que recebe pedido do usuário).
3. **Materialize cada papel do squad como connected agent**, com (a) history-off, (b) component collection compartilhada apontando para SharePoint que reflete `_shared/`, (c) Entra Agent ID com permissions mínimas, (d) DLP policy strict.
4. **Encapsule o pipeline crítico em agent flow determinístico** com multistage approval entre cada papel. Para o qa-critic adversarial com modelo distinto: enquanto o BYOM per-agent não é GA, implemente o qa-critic em **Microsoft Agent Framework 1.0** (Foundry-hosted ou in-process) e chame-o do agent flow via HTTP/MCP — o modelo Claude/Llama nesse subagente é independente do GPT do orquestrador no Copilot Studio.
5. **Audit/trace**: Application Insights + Purview + export para ADLS Gen2 imutável; cada decisão do qa-critic com hash do prompt/resposta gravado em Dataverse.
6. **Quando Copilot Studio não é a escolha**: lógica que exige Python/orquestração customizada (Sequential/Group-Chat/Magnetic patterns), fine-tuning, controle de temperature/top-p/seed (Copilot Studio **não expõe** esses controles mesmo com BYOM), evaluation gates programáticos, multi-agent deeply coupled — vá direto a **Microsoft Agent Framework + Foundry Agent Service**.

| **Microsoft Agent Framework 1.0 (SDK)** | qa-critic com modelo distinto, orquestrações Sequential/Group-Chat/Magnetic, middleware para anti-alucinação/RAI, A2A entre runtimes | Quando time é apenas de makers low-code; quando não há time para operar Azure |
| **Azure AI Foundry Agent Service** | Hospedagem managed do pipeline regulado, com tracing/evals integrados, modelo escolhido a dedo, RBAC Azure, Purview governance | Cenários simples sem necessidade de controle de modelo/orquestração |
| **Agent Builder (M365 Copilot)** | Não recomendado para este framework — teto baixo (só Q&A declarativo) | Qualquer caso com lógica/aprovação/regulação |

## Recommendations

**Stage 1 — Foundation (0–30 dias)**
- Manter o repositório `metacognition-framework` como **fonte normativa única** (não migrar `_shared/`, validation-gamp5, ADRs).
- Provisionar 3 ambientes Power Platform como **Managed Environments** (DEV/TEST/PROD), com DLP policies strict por ambiente, source control Git/Azure DevOps ativado, Pipelines configurados.
- Habilitar **Entra Agent Identity** no environment (preview) para que cada agente tenha service principal próprio com permissions visíveis no Entra admin center.
- Conectar Application Insights desde o DEV (não esperar prod) e exportar transcripts via Azure Synapse Link para ADLS Gen2 com retenção mínima de 6 anos (alinhado a Annex 11/Part 11/ANVISA), já que o default Dataverse é 30 dias.

**Stage 2 — Squad mapping (30–90 dias)**
- Criar um **agente principal "PMO"** com Generative Orchestration ligada e instruções derivadas do AGENT-FRAMEWORK.md.
- Criar **connected agents** separados para explorer (read-only, sem write tools), developer, qa-critic, docops. Em cada um: desmarcar "Pass conversation history" (default-off como SOP), Entra Agent ID com escopo mínimo, DLP fechado.
- Criar uma **Component Collection "shared-skills"** que aponta para um SharePoint contendo cópia somente-leitura de `_shared/` (atualizado por CI quando o Git é alterado). Conectar todos os agentes a essa collection.
- Encapsular o fluxo crítico (qualquer tarefa "decisão sensível/regulada/irreversível") em **agent flow com multistage approval** — não confiar na generative orchestration para a ordem.

**Stage 3 — qa-critic adversarial (90–180 dias)**
- **Se BYOM Primary Response Model atingir GA** (monitorar release plan Microsoft): configurar developer=GPT-5 e qa-critic=modelo distinto (Claude/Llama) diretamente via Settings → Responses no Copilot Studio.
- **Se ainda em preview** (bloqueador GxP por data residency): implementar o qa-critic como agente em **Microsoft Agent Framework 1.0** (hospedado em Foundry Agent Service ou Azure Container Apps na região Brazil South/EU), chamado do agent flow do Copilot Studio via HTTP+OAuth2. Esse agente carrega o checklist binário de 6 critérios + edge cases.

**Stage 4 — Regulatory hardening (paralelo, contínuo)**
- Aplicar GAMP 5 2nd Ed. CSA risk-based: classificar o sistema (category 4 — configured product), executar IQ/OQ/PQ, manter trace matrix entre `requirements.md`/`validation.md` (Git) e agentes/flows do Copilot Studio.
- Para 21 CFR Part 11 / Annex 11 / RDC 658: implementar **assinatura eletrônica** fora do Copilot Studio (Power Apps + Entra ID + audit log + hash) já que não há nativo. Cada gate humano de approval grava registro assinado em tabela Dataverse com hash do conteúdo aprovado.
- Manter **ALCOA+** via combinação: Application Insights (Attributable/Legible/Contemporaneous), Dataverse audit (Original/Accurate), ADLS Gen2 imutável (Complete/Consistent/Enduring), Purview retention locks (Available).

**Benchmarks que mudam a recomendação**
- Se Microsoft anunciar **atestação GxP/GAMP 5 específica para Copilot Studio** (não apenas Azure/M365): pode-se centralizar mais lógica regulada dentro da plataforma.
- Se **BYOM Primary Response Model** for promovido a GA com data residency garantida em Brazil South: ativa-se o qa-critic adversarial nativo, eliminando a necessidade do Agent Framework externo para esse papel.
- Se Copilot Studio expor **prompt versioning granular** (diff por linha de instrução) e **assinatura eletrônica 21 CFR Part 11 nativa**: revisar a fronteira "o que fica no Git × o que migra para Solutions".
- Se o **A2A protocol** + Microsoft 365 Agents SDK consolidar GA pleno (anunciado para abril/2026) com tracing cross-runtime: simplifica a coexistência Copilot Studio ↔ Agent Framework.

## Caveats

1. **Velocidade de mudança**: Copilot Studio teve mudanças mensais relevantes ao longo de 2025–2026 (multi-agent, MCP GA, Component Collections GA, Workflows preview, BYOM agent-level preview). Datas e status migram rápido; tudo classificado [EMERGENTE] deve ser revalidado contra Microsoft Learn antes de decisão.
2. **Preview ≠ produção regulada**: várias capacidades-chave para este framework (BYOM agent-level, Entra Agent ID, Workflows redesign) ainda estão em public preview com cláusula explícita "shouldn't be used for production" e processamento de dados possivelmente fora da fronteira geográfica do tenant. **Não use preview features em ambiente farmacêutico produtivo.**
3. **Custo é estimativa**: os números de Copilot Credits e USD foram extraídos de blogs/Microsoft Learn de 2025–2026 e variam conforme design do agente, modelo, tier de licença M365 Copilot incluído, e região. Há discrepâncias menores entre fontes (Microsoft Learn fala em "per 10 tokens"; análises de terceiros como CloudZero referem-se a "per 10 responses" para reasoning models) — em caso de dúvida, prevaleça a documentação oficial. Faça PoC com Copilot Credit Estimator antes de comprometer orçamento.
4. **Sem atestação GxP de Copilot Studio**: a Microsoft fornece "GxP qualification guidelines" para Office 365 e suporte a HIPAA/FedRAMP/etc., mas **Copilot Studio especificamente não consta na lista de serviços com atestação GxP independente**. A validação operacional do uso regulado segue sendo responsabilidade do regulado (CSA/GAMP 5 risk-based).
5. **Lock-in real**: a estratégia híbrida proposta mitiga, mas não elimina, dependência de Dataverse + Power Platform + Copilot Credits. Mantenha o repo Git como exit-strategy: ele preserva a inteligência do framework independente da plataforma de execução.
6. **Generative orchestration é probabilística**: mesmo com instruções perfeitas, pode escolher um tool diferente entre uma conversa fresca e uma longa. Para pipelines regulados, **prefira agent flows** (determinísticos) e use generative orchestration só onde "self-assembly" é valor.
7. **Comparação com GitHub Copilot custom agents**: a estrutura `.agent.md` + subagents + handoffs do GitHub Copilot é hoje **conceitualmente mais aderente** ao framework (fresh context por subagente, modelo selecionável por agente, instruções em Markdown puro versionado). Para o squad de engenharia continuar trabalhando no framework, **GitHub Copilot custom agents permanece o ambiente nativo**; Copilot Studio é a "vitrine" para usuários finais e processos de negócio.
8. **Cada cliente, cada PoC**: o mapa acima é uma diretriz; antes de comprometer com migração, valide com PoC focada em uma feature crítica (sugestão: o gate humano com multistage approval em ambiente regulado) e meça latência, custo em créditos, completude do audit-log.
